Exoskeleton Code Project

Repository Scope

  • Project type: STM32WB55 BLE exoskeleton sensor, recording, and desktop diagnostic system.
  • Active transport architecture: BLE-first.
  • Retained but inactive transport stack: RS485 recording protocol.
  • Firmware projects:
    • Master/: hub firmware.
    • Node/: leaf/node firmware.
  • Shared code:
    • LIBRARY/: custom application code, shared protocol headers, sensor drivers, storage drivers, retained transport code.
  • Host tool:
    • DesktopTools/Exoskeleton.html: Web Bluetooth browser tool.
  • Build system: STM32CubeIDE GCC.
  • MCU target: STM32WB55CCUx / STM32WB55CCU6.
  • STM32Cube firmware package: STM32Cube FW_WB V1.24.0.
  • Main firmware files use .c extension but are compiled with g++.

Functional

  • The system collects IMU data from a hub and BLE leaf nodes.
  • The hub exposes a BLE service to the browser.
  • The hub also acts as a BLE central for leaf nodes.
  • Leaf nodes advertise the same custom BLEPipe service.
  • Live data can be streamed without recording.
  • Recording data is stored locally first.
  • Hub recording storage target: SD card.
  • Node recording storage target: external W25Q256 SPI flash.
  • Recorded sessions are transferred after recording completion.
  • The browser verifies recorded-session header CRC and payload CRC.
  • The browser decodes recorded BNO85 and ICM45686 samples.
  • The browser plots live and recorded signals.
  • The browser can export selected samples as CSV.

BLEPipe GATT

  • Service name: BLEPipeService.
  • Service short name: BLEPipe.
  • Service UUID: 3f881000-b4a5-4f7c-9b60-98e0b5c8a000.

Characteristics:

  • PipeDataTx
    • UUID: 3f881001-b4a5-4f7c-9b60-98e0b5c8a000
    • Property: notify.
    • Usage: live samples, hub aggregate samples, raw forwarded payloads.
  • PipeControlRx
    • UUID: 3f881002-b4a5-4f7c-9b60-98e0b5c8a000
    • Properties: write, write without response.
    • Usage: incoming commands.
  • PipeControlTx
    • UUID: 3f881003-b4a5-4f7c-9b60-98e0b5c8a000
    • Properties: notify, indicate.
    • Usage: command responses, ACK, NACK, control relays.
  • PipeStatusTx
    • UUID: 3f881004-b4a5-4f7c-9b60-98e0b5c8a000
    • Properties: read, notify.
    • Usage: readiness, topology, heartbeat, link stats, events, logs, errors, reliable-transfer status.
  • PipeConfigRw
    • UUID: 3f881005-b4a5-4f7c-9b60-98e0b5c8a000
    • Properties: read, write.
    • Usage: config lane.

BLEPipe Frame

  • Protocol version: 1.
  • Max notification payload: 244 bytes.
  • Header length: 20 bytes.
  • CRC length: 2 bytes.
  • Max application payload: 222 bytes.
  • CRC type: CRC-16/CCITT.
  • CRC coverage: BLEPipe header plus application payload.

BLEPipe IDs:

  • Hub: 0x0001.
  • Leaf 1: 0x0101.
  • Leaf 2: 0x0102.
  • Leaf 3: 0x0103.
  • Leaf 4: 0x0104.
  • Broadcast: 0xFFFF.
  • Browser/phone in desktop tool: 0x1000.

BLEPipe lanes:

  • DATA_TX: LEAF_SAMPLE, HUB_AGGREGATE, RAW_FORWARD.
  • CONTROL_RX: COMMAND, TIME_SYNC, CONFIG_SET, STREAM_CONTROL.
  • CONTROL_TX: COMMAND_RESP, ACK, NACK.
  • STATUS_TX: STATUS, TOPOLOGY, LINK_STATS, EVENT, LOG, ERROR.
  • CONFIG_RW: CONFIG_READ, CONFIG_WRITE, ROUTING_TABLE, DEVICE_INFO, STREAM_PROFILE.

Live Stream Data Flow

Live stream path:

  1. Browser connects to hub BLEPipe service.
  2. Browser writes a STREAM_CONTROL BLEPipe frame to PipeControlRx.
  3. Hub receives the command in the custom BLE app event path.
  4. Hub updates stream state.
  5. Hub samples BNO85 and ICM45686.
  6. Hub packs each sample in a BLE_STREAM_V2 envelope.
  7. Hub sends sample notifications through PipeDataTx.
  8. Browser receives notifications.
  9. Browser validates BLEPipe frame.
  10. Browser parses BLE_STREAM_V2.
  11. Browser decodes sensor payload.
  12. Browser appends trace points to the plot.

Live stream command IDs:

  • Start stream: 0xA0.
  • Stop stream: 0xA1.
  • Set stream interval: 0xA2.

BLE_STREAM_V2 :

  • Frame ID: 0xB1.
  • Version: 1.
  • Header fields:
    • Node ID.
    • Sensor ID.
    • Sequence.
    • Timestamp in milliseconds.
    • Payload length.
  • Sensor IDs:
    • BNO/IMU: 0x01.
    • ICM45686: 0x02.
    • Flex/analog decoder support: 0x03.

Leaf live-stream path:

  1. Leaf sends BLEPipe data notification.
  2. Hub BLE central client receives leaf notification.
  3. Hub validates/decodes BLEPipe.
  4. Hub forwards data/control/status to the browser through its own BLEPipe service.
  5. Browser treats forwarded leaf samples as node-specific traces.

Recording Data Flow

Start Command

  • Browser sends a record start command over BLEPipe.
  • Start command struct: StartRecordMessage.
  • Start command fields:
    • Command.
    • Session ID.
    • Lead time in microseconds.
    • Duration in milliseconds.
  • Hub receives the command through PipeControlRx.
  • Hub routes the command in Master/Core/Src/main.c.

Hub Coordination

  • Hub tracks connected BLE leaves.
  • Hub tracks ready BLE leaves.
  • Hub sends prepare/start messages to selected leaves.
  • Hub waits for leaf prepare/app-ready responses.
  • Hub sends commit when required leaves are prepared.
  • Hub starts local SD recording.
  • Nodes start local flash recording.

Recording start heartbeat phases:

  • 0x01: wait app ready.
  • 0x02: reset cooldown.
  • 0x03: prepare sent.
  • 0x04: wait prepare ACK.
  • 0x05: app ready acquired.
  • 0x06: commit start.
  • 0x20: node reset.
  • 0x21: node prepare.
  • 0x22: node commit.
  • 0x23: node abort.
  • 0x24: node ready wait.

Node Recording

  • Node recording class: exo::NodeRecordingApp.
  • Default duration: 10000 ms.
  • Default lead time: 300000 us.
  • Record tick: 10 ms.
  • Effective recording rate target: 100 Hz.
  • BNO batch size: 4 samples.
  • ICM batch size: 8 samples.
  • Storage target: W25Q256 SPI flash.
  • Upload reader class: exo::SessionUploadReader.
  • Completion notification: RecordDoneMessage.

Hub Recording

  • Hub recorder class: exo::MasterSdSessionRecorder.
  • Storage target: SD card through FatFs.
  • Session root directory: /SESSIONS.
  • Final master session path: /SESSIONS/MREC.BIN.
  • Max BNO samples: 1200.
  • Max ICM samples: 2400.
  • BNO buffer samples: 8.
  • ICM buffer samples: 32.
  • Copy buffer size: 256 bytes.

Session Format

  • Session magic: 0x584F5345 (ESOX).
  • Header size: 56 bytes.
  • Complete flag: 0xA5.
  • Format macro: EXO_SAMPLE_FORMAT_VERSION.
  • Default format version: 3.
  • Allowed format versions: 2, 3.
  • Invalid format versions cause compile-time error.
  • BNO85 sensor ID: 0x01.
  • ICM45686 sensor ID: 0x02.
  • Session payload order:
    • Session header.
    • BNO85 payload region.
    • ICM45686 payload region.
  • Header CRC function: session_header_crc.
  • Payload CRC: CRC-32 over BNO85 plus ICM45686 payload regions.

Reliable Transfer

  • Protocol header: RecordReliableFrameHeader.
  • Reliable protocol version: 6.
  • Reliable magic: 0x5845 (EX).
  • Default chunk size: 180 bytes.
  • Default credit: 16.

Recording command :

  • ListSessions: list sessions.
  • FetchSession: fetch session.
  • SessionChunk: legacy/direct session chunk.
  • ChunkAck: chunk acknowledgement.
  • SessionCompleteAck: transfer completion acknowledgement.
  • EraseSession: erase session.
  • PrepareRecord: prepare delayed synchronized record.
  • CommitPreparedRecord: commit prepared record.
  • AbortPreparedRecord: abort prepared record.
  • ReliableFrame: reliable transfer frame.

Reliable frame types:

  • Manifest: declares transfer metadata.
  • ManifestAck: opens receive window and credit.
  • AckWindow: acknowledges received window/progress.
  • NackRange: requests retransmission of missing chunks.
  • Chunk: carries payload bytes.
  • Pause: pauses source.
  • Resume: resumes source.
  • Cancel: cancels transfer.
  • VerifyOk: receiver verified transfer.
  • VerifyFail: receiver verification failed.
  • BusyNotOwner: receiver is busy with another source/session.
  • SourceWaiting: source has no current credit or is waiting.
  • CommitDone: source finished commit/cleanup step.

Reliable transfer path:

  1. Source sends RecordDone.
  2. Receiver creates or queues transfer state for (session_id, source_id).
  3. Source sends Manifest.
  4. Receiver validates manifest.
  5. Receiver sends ManifestAck.
  6. Source sends chunks while credit is available.
  7. Receiver records chunk bitmap.
  8. Receiver sends AckWindow periodically.
  9. Receiver sends NackRange for gaps.
  10. Source retransmits missing ranges.
  11. Receiver verifies CRC.
  12. Receiver sends VerifyOk or VerifyFail.
  13. Source sends CommitDone.
  14. Receiver sends or handles SessionCompleteAck.
  15. Source may erase/reset local completed session state.

Main Data Paths

Live stream:

Sensors -> STM32 sampler -> BLE_STREAM_V2 payload -> BLEPipe DATA_TX -> browser notification -> decoder -> plot

Hub-record path:

Hub sensors -> MasterSdSessionRecorder -> SD card -> reliable transfer/notification -> browser -> CRC check -> decoder -> plot/export

Node-record path:

Node sensors -> NodeRecordingApp -> W25Q256 flash -> RecordDone -> Manifest -> Chunk/Ack/Nack -> Verify -> browser decode

Hub relay path:

    11: ## High-Level System View
    12: 
    13: At a system level, the project behaves like this:
    14: 
>   15: - A `Node` is a remote sensing endpoint with its own STM32WB55, IMU sensors, RS485 transport, and optional flash storage for local recording.
    16: - The `Master` is the central coordinator. It has its own sensors, manages BLE, talks to the nodes over RS485, records its own local data to SD, and acts as the gateway between RS485 and the browser UI.
    17: - `DesktopTools` connects to the master over BLE using Web Bluetooth, sends commands, receives live IMU packets and recorded data, performs acknowledgements and recovery control, and turns raw payloads into plots and CSV exports.
    18: 
    19: The practical control path is:
    20: 

    21: `DesktopTools -> BLE -> Master -> RS485 -> Nodes`

    22: 
    23: The practical data return path is:
    24: 
    25: `Nodes/Master sensors -> local buffers/storage -> RS485 and/or BLE notifications -> DesktopTools decode/reassemble -> plots/log/export`
    26: 

    27: ## What `Master/` Does
    28: 
    29: `Master/` is the main hub firmware. It is not just another sensor board. It is the coordinator, BLE server, recording bridge, retransmission controller, and data egress point for the whole system.
    30: 

    31: ### Main responsibilities of the master
    32: 
    33: The master firmware is responsible for:
    34: 
>   35: - Booting and initializing the STM32WB platform, clocks, GPIO, DMA, RTC, I2C, SPI, UART, RF, BLE stack, and SD/FATFS plumbing.
    36: - Sampling its own onboard/local sensors through the `HubSensorTestApp` path.
    37: - Managing the BLE GATT service and its characteristics for IMU streaming, command writes, command acknowledgements, recording data, and recovery/control traffic.
    38: - Receiving commands from the browser over BLE and dispatching them into local actions or RS485 actions.
    39: - Discovering and managing remote nodes on the RS485 network.
    40: - Starting synchronized recordings across master and nodes.

    41: - Recording the master’s own local data to SD card storage using the SD session recorder path.
    42: - Receiving node recording traffic over RS485 and forwarding or bridging it toward BLE.
    43: - Running the reliable recording protocol: manifests, chunk windows, acknowledgements, NACKs, retransmissions, verify, commit, pause/cancel, and resume-like resynchronization.

    44: - Recovering UART DMA receive state when the RS485 receive side becomes busy or faulted.

    45: 
    46: ### Role of `Master/Core/Src/main.c`
    47: 

    48: `Master/Core/Src/main.c` is the real orchestration center for the firmware-specific behavior. It does far more than normal Cube-generated startup code. Its user sections instantiate the application objects and implement the project-specific control logic.
    49: 

    50: Key things defined there:
    51: 
    52: - `HubSensorTestApp` for collecting local hub/master sensor samples.
>   53: - `MasterRecordingController` for RS485-side recording coordination with nodes.
    54: - BLE send callbacks that wrap `Custom_APP_SendRecordFrame`.
    55: - The RS485 LPUART DMA receive buffer and recovery logic.
    56: - A full local recording state machine for master-owned recordings.
    57: - Recovery queues for retransmission jobs.
    58: - BLE command handlers through `exo_hub_ble_write(...)`.

>  119: ### Master RS485 role
   120: 
   121: The master is the only device that talks both BLE and RS485 in the end-user path.
   122: 
   123: On the RS485 side, the master:
   124: 

   125: - Initializes `hlpuart1` receive-to-idle DMA.
   126: - Monitors UART busy/error conditions.

   127: - Aborts and restarts DMA reception when needed.
   128: - Uses `MasterRecordingController` to coordinate node-side recording and chunk transport.

   129: - Tracks discovered nodes and exposes node discovery status back to the desktop.
   130: 

   131: This makes the master a protocol translator and scheduler:

   132: 
   133: - BLE is packetized around GATT writes/notifications and browser timing.
>  134: - RS485 is packetized around UART/DMA transport and multi-node coordination.
   135: 
   136: The master absorbs these differences so the browser can work with a single device and a single control model.

   167: ## What `Node/Core/` Does
   168: 
>  169: `Node/Core/` is the hardware/application entry layer for a remote sensing node. It brings up the MCU, sensor buses, RS485 UART path, flash SPI path, and runtime services that the node-specific recording logic depends on.
   170: 
   171: Important distinction:
   172: 
   173: - `Node/Core/` is where hardware is initialized and the top-level runtime loop lives.
   174: - The BLE stack and profile files still exist under `Node/STM32_WPAN/`, but the node’s practical project-specific role is defined by `Node/Core/Src/main.c`.

   183: - Loading or applying the runtime node ID.

   185: - Sampling and storing node-local sensor data during a recording session.
   186: - Answering RS485-side recording requests from the master.

   244: ### Node RS485 role
   245: 

   246: The node does not sit on the BLE front end in the same way the master does. Its operational identity in this system is as an RS485 recording endpoint.
   247: 
   248: The node responder:
   249: 

   250: - listens on `hlpuart1`
   251: - reacts to receive complete / receive idle / receive error callbacks

   252: - processes RS485 discovery and recording protocol frames
   253: - starts local recording when requested
   254: - returns data chunks or retransmissions
   255: 

   256: The callback wiring in `Node/Core/Src/main.c` makes that explicit:
   257: 

>  258: - `HAL_UART_RxCpltCallback(...)`
   259: - `HAL_UARTEx_RxEventCallback(...)`
   260: - `HAL_UART_ErrorCallback(...)`
   261: 
   262: All three feed into `node_rs485_recording`.

   264: ### Node direct BLE behavior

   265: 

   266: There is still BLE framework code in the node project, but from the project behavior in `Node/Core/Src/main.c`, the node’s project-specific BLE write handling is limited compared with the master.
   267: 

>  268: The exposed `exo_node_ble_write(...)` path mainly supports:
   269: 
   270: - `StartRecord`
   271: - completion acknowledgement
   272: - reset-to-idle-and-erase
   273: 

>  274: That indicates the node is not intended to be the primary operator-facing BLE endpoint. The master is. The node’s main production path is RS485 responder + local storage + replay.

   276: ## What `DesktopTools/` Does
   277: 
   278: `DesktopTools/` is the operator console for this system. It is a browser-based toolset, not embedded firmware. It connects to the master via Web Bluetooth and acts as:
   279: 

   487: 
   488: 1. User enters session parameters in the desktop UI.
   489: 2. Desktop sends `STOP_STREAM` first.
   490: 3. Desktop sends `RESET_RECORD_STATE`.
   491: 4. Desktop sends the binary `StartRecord` message.
>  492: 5. Master receives the BLE write through `custom_app.c` and dispatches it to `exo_hub_ble_write(...)`.
   493: 6. Master validates:
   494:    - message length
   495:    - duplicate/replay conditions
   496:    - current transfer/recording ownership state
   497: 7. Master arms its local recorder.

>  498: 8. Master triggers the node-side recording control through the RS485 recording controller.
   499: 9. Master sends a `CMD_ACK` response back to the desktop.
   500: 10. Desktop marks the request as accepted and waits for record completion rather than assuming transfer begins immediately.
